# Platform form and route inventory

Read-only source inventory from public commit `85e07e0` and the Cloud overlay. Counts describe route modules, not distinct runtime states. Public has 75 TSX route modules plus two nonvisual handlers (`api.$.ts`, `session.ts`). Cloud adds 14 overlay route modules: 11 visual workspace/account routes, two API proxies, and a nonvisual health handler.

## First visual priorities

1. **Application creation and configuration** — `/applications/new`, `/applications/:id/configure`, and `/applications/:id/services/new` converge on `DeploymentForm`. The form combines entry-mode selection, application policy, every service, conditional runtime type, resources, environment rows, files, review, secrets, and deployment. In a multi-service application all service editors are expanded in one document, so the user must repeatedly parse the same long field sequence.
2. **Add service** — `/applications/:id/services/new` presents catalog/Compose, HTTP function, and container-image creation as three equally prominent paths before handing the draft to the full deployment form. The route contains two forms and multiple availability/collision branches; progressive choice is weak.
3. **Service update** — `/applications/:id/configure?service=` still uses the same broad editor as whole-application configuration. Runtime type, image/function, command, registry, port, size, replicas, custom resources, environment, exposure, recovery, and review compete even when the user intends one small edit.
4. **Environment variables and secrets** — `/applications/:id/environment?service=` is safer because it has a dedicated review, conflict merge, and preserved draft. `EnvironmentFields` is still a dense row editor with name/value, show/hide, secret conversion, delete, dotenv paste/import, inherited application values, and shared-secret impact.
5. **Build creation/edit** — `BuildForm` is the next largest wizard: repository/provider, revision/context, build method-specific fields, runtime service, environment, registry, resources, paths, triggers, and review.

## Cloud-only overlay

Cloud inherits every public engine route through composition, then adds 11 visual routes: `/workspaces`, `/workspaces/plans`, `/workspaces/team-access`, `/workspaces/:workspace`, `/workspaces/:workspace/team`, `/workspaces/:workspace/waitlist`, `/workspaces/:workspace/approvals`, `/workspaces/:workspace/approvals/:approval`, `/workspaces/:workspace/roles/new`, `/workspaces/:workspace/roles/:role/edit`, and `/invite`. The remaining nonvisual overlay modules are `/api/node/$` and `/cloud-api/$` proxies, plus `/healthz`.

Key components are `CloudOnboarding`, `HostedCompute`, `WorkspaceCompute`, `CloudCollaboration`, and `NodeEnrollment`. Branches cover workspace creation/naming, personal versus team access, plan selection, hosted versus own-server compute, region/size/capacity, node enrollment, waitlist, approvals, invitations, members and custom roles. The main risk is that account, billing, workspace identity, compute allocation, and collaboration are shown as neighboring settings even though they have different ownership and consequence levels. Cloud review must also verify the composed engine forms, because the overlay does not replace the public application/service editors.

## Existing fixture harness assets

The current managed worktree does not contain the old ignored global harness, but the primary checkout does. It can be copied or adapted into a new ignored harness without changing product source.

- `work/ui-migration/global-review/`: full application router harness with `main.tsx`, `review.mjs`, `edge.mjs`, `help*.mjs`, `probe.mjs`, `routes.json`, proxy fixtures and 65-case historic screenshots. Existing route map includes application new/import/configure/environment/source/detail and broad settings/infrastructure families.
- `work/ui-migration/operations-fixture/`: strongest reusable API fixture for the named flows. It already has application/service records, environment conflict and failed-plan/deploy states, service secrets/shared-secret states, template add/review states, TOML expanded states, network and project states, plus `main.tsx`, `server.mjs`, QA scripts and proxy/template fixtures.
- `work/ui-migration/dashboard-fixture/`: application and service catalog layouts, environment failure retention, required-select validation and keyboard/layout scripts.
- `work/ui-migration/build-fixture/`: dedicated build create/edit/review fixture and server.
- `work/ui-migration/page-inset-review/`, `project-review/`, `alarms-review/`, `git-provider-review/`, `smtp-readiness-review/`, and `public-tcp-policy-review/`: narrower route/API fixtures useful for settings and policy branches.

The old `global-review/routes.json` predates several current routes: services/new, previews/new, notifications, certificates, alarms, databases, DNS providers, secret providers, SMTP, roles and Cloud workspaces. A new platform harness should extend the route map rather than treating the old 65 cases as current coverage. Fixture screenshots are development evidence only and must remain explicitly labeled artificial.

## Audit-state matrix required next

For each mutating form, render create, edit with saved values, validation error, backend failure with draft retention, review/confirmation, permission denied, loading and unavailable dependencies. Check Ink and Paper themes, 1440/390/320 widths, keyboard focus order, touch disclosure behavior, real element bounds and long values. For repeatable rows, include empty, one row, many rows, long names/values, secret-hidden and inherited/shared states. For conditional forms, capture every branch listed above rather than only the default selection.
