# Slack integration

Slack notifications are a Hakopod Pro feature. Open **Settings → Integrations → Slack** to connect it. On a self-hosted installation, an administrator creates a Slack app from the manifest returned by `GET /api/v1/integrations/slack`, installs it into a workspace, and completes the OAuth connection. The redirect URL is the dashboard's `/api/integrations/slack/callback` proxy, which keeps the browser session cookie out of the engine API. Hakopod requests only `chat:write`, `channels:read`, and `groups:read`. The selected channel must already contain the bot.

On Hakopod Cloud, a workspace owner authorizes the published Hakopod Cloud Slack app for that workspace; Cloud owns its OAuth credentials and enforces the workspace Pro entitlement. A BYO managed Cloud node does not create another Slack app. Its browser administrator configures an enrollment-bound relay that forwards only its scoped committed events to Cloud.

The integration has a selectable catalog of alarm, audit, deployment, application and service events. Alarms cover opened and resolved incidents; audit covers recorded Hakopod audit events. Deployment events cover queued, started, succeeded, failed, cancelled, superseded, rollback requested and cancellation requested. Application events cover created, accepted configuration changes, renamed and deleted applications. Service events cover added, removed, renamed, accepted configuration, image, variables, resources, scaling, suspension, resume, restart, network, storage, health-check, placement, command and delivery changes, plus update started, ready, failed, job scheduled, job completed and certificate renewed.

Slack messages use a fixed event label and bounded operational identifiers: project, environment, application name or ID, service, deployment, revision and recovery context when they apply. Alarm messages contain only their fixed label plus project, environment, application ID, resource and alarm ID. They do not include alarm summaries, command output, service messages, images, commands, variable values, secret values, specifications or log bodies. It stores OAuth client credentials and bot tokens only as authentication-key ciphertext. It does not claim exactly-once delivery: each committed source event has one durable outbox row, and Slack may receive a retry after a connection failure. Slack responses with HTTP 200 and `ok:false` are treated as failures, while rate limits and transient failures use bounded retries and `Retry-After`.

Every authorization attempt captures an installation-wide Slack generation. Connecting, changing delivery settings, and disconnecting advance that generation, so a late OAuth callback cannot replace a newer configuration or recreate a disconnected one.

Hakopod evaluated [Hookdeck Outpost](https://github.com/hookdeck/outpost) and its [webhook destination model](https://hookdeck.com/docs/outpost/destinations/webhook) for a future shared event carrier. It has no native Slack OAuth or destination provider, and its current self-hosted deployment needs Redis, a message queue, and PostgreSQL. Hakopod therefore does not add it as runtime infrastructure for this single integration.

The durable Slack queue holds at most 10,000 pending or leased events. During a prolonged outage, new notification events above that bound are intentionally dropped so alerts cannot grow the installation database without limit. Delivery history retains terminal records for 30 days. Cloud shared-runtime delivery uses a trusted static source identity. BYO managed Cloud nodes use the enrollment-bound relay described below.

For a BYO managed Cloud node, an installation administrator configures the source in the browser. The relay then uses a separate, short-lived machine key with only the `slack:relay` permission, scoped to that source's project and environment, to claim one leased event at a time. The relay never supplies or receives a Cloud workspace ID from Hakopod; it forwards the source-bound event to Cloud and acknowledges the exact delivery lease as accepted, retry, or skipped. Cloud verifies the workspace's Pro entitlement before it accepts the event.
